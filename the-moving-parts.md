# The Moving Parts

SatDump is easier to reason about once you can name its parts. There are five, and every success or failure you will ever see belongs to one of them.

**The program.** Two executables share one engine: `satdump`, the command-line program this guide drives, and `satdump-ui`, the graphical program with windows, spectrum displays and buttons. They are the same machinery wearing different clothes; a decode that works in one works in the other, and the lab used the command line because it leaves a written record of everything it did. A third helper, `satdump_sdr_server`, lets a radio connected to one computer serve another — mentioned here so the name never surprises you.

**Pipelines.** A pipeline is a recipe, stored as a text file in a format called JSON, that says: for *this* satellite's transmission, take input of *this* kind, run *these* processing modules in *this* order, and make *these* products. The installed program keeps its recipes in a `pipelines` folder — the lab counted **71 files holding 184 pipelines** (transcript `t01`). Recipes can be read, and the guide reads several: knowing that the NOAA APT recipe contains a demodulator module followed by a decoder module tells you exactly what kind of file each stage expects, which is the key to the troubleshooting chapter. Pipelines are data, not code, and the community adds new ones as new satellites launch.

**Modules.** Inside a pipeline, each step is a module: a demodulator that turns a radio waveform into a stream of bits, a decoder that turns bits into frames and checks their error-correction, an instrument module that turns frames into calibrated images. Modules are compiled code, many of them loaded as **plugins** — separate library files the program loads at startup. The decode log's first minute is mostly the program loading plugins by name, and it is honest about the ones it cannot load: on the lab machine, the plugins for Airspy and bladeRF radios complained about missing libraries and were skipped, which mattered not at all because no such radio was attached. A pipeline only needs its own modules to be present.

**Products.** What comes out. For an imaging satellite, products are pictures: one per instrument channel, enhancement variants (contrast-stretched, false-colour composites), and map-projected versions. Alongside the pictures, most pipelines write a small `dataset.json` naming the satellite and the recording's time, and a `product.cbor` file holding the underlying data in a compact binary form, so other programs can rebuild products later without decoding again. Chapter 7 reads the lab's product set file by file.

**Orbital data.** To draw a map under a picture, SatDump must know where the satellite *was*. It keeps a file of **TLEs** — two-line elements, the standard compact description of an orbit, published for thousands of objects. The lab watched SatDump download this file by itself at first launch: 2.4 MB, **15,900 orbits loaded** (transcript `t05`). No account, no configuration; it refreshes the file when it is stale. Chapter 8 shows what changes when the program knows the time and place of a pass — and what it quietly refuses to do when it doesn't.
